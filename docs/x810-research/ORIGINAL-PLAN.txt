# Mission

You are responsible for researching, engineering, testing, and documenting a native-mainline Linux/Fedora port for a **Samsung Galaxy Tab S9+ Wi-Fi, SM-X810, codename `gts9pwifi`, Qualcomm SM8550/Kalama**, using a real tablet that is available to you over ADB.

The finished system should provide:

1. A current stable Fedora desktop running natively on the tablet's **internal UFS**.
2. Mainline or near-mainline Linux based on the proven Tab S9 work, not Android userspace/chroot/proot.
3. One UI retained alongside Fedora.
4. No microSD dependency at any stage of the finished installation.
5. Internal-UFS dual boot.
6. A reliable **Fedora → Reboot into One UI** mechanism.
7. Preferably also **One UI → Reboot into Fedora**, using a rooted Android-side switcher if appropriate.
8. TWRP/Download Mode recovery.
9. Reproducible source, scripts, documentation, hardware findings, build artifacts, and test evidence.
10. An architecture that can be maintained and updated rather than a one-off manually patched image.

The owner does **not care about preserving current userdata**. You may wipe Android data, repartition the UFS, recreate `userdata`, and create a dedicated Linux partition when appropriate.

However:

* Do not destroy partitions unnecessarily.
* Do not overwrite bootloader/EFS/calibration data.
* Do not update the Samsung bootloader merely to obtain a newer firmware.
* Preserve the currently useful unlocked bootloader state unless compelling evidence requires otherwise.
* The current tablet is believed to be bootloader revision / SEC bit **5**, unlocked. Verify this yourself.
* Do not assume any SM-X710 or SM-X910 partition sizes, GPIOs, DT selectors, component identities, memory carveouts, firmware selections, battery parameters, or other board-specific data apply to SM-X810.
* The tablet starts in a working One UI installation with **wireless ADB already connected**.
* There is **no microSD-based development path**. Do not design around one.
* Internet research is expected. Use primary sources wherever possible.
* You are expected to draw your own conclusions from source and device evidence rather than treating this document as authoritative hardware truth.

This is a research-and-engineering assignment, not a rote implementation assignment.

---

# Core engineering philosophy

Use the following evidence hierarchy when facts disagree:

**Highest confidence:**

1. Measurements from the actual connected SM-X810.
2. Exact stock firmware corresponding to the connected tablet.
3. Samsung/Qualcomm downstream device-tree/kernel source for the exact X810 family.
4. Decompiled stock X810 DTB/DTBO.
5. Active mainline Linux ports for SM-X710 and SM-X910.
6. Samsung SM8550 common source.
7. Recovery-device trees and custom kernels.
8. Forum posts, issue discussions, and third-party claims.

Never promote an inference into a hardware fact without recording how it was established.

For every significant hardware conclusion, record:

* fact;
* confidence;
* source;
* exact source commit or firmware build;
* whether it was measured on X810;
* whether it came from X710/X910 prior art;
* what experiment validated it;
* what evidence would falsify it.

When sibling devices disagree, assume the X810 may be unique until evidence establishes otherwise.

# Mandatory recovery-access gate

Wireless ADB works while Android is running. It is **not sufficient proof of recovery access**.

Before repartitioning or replacing the main boot set, establish a path that remains available if Android no longer boots.

At least one of these must be proven:

* TWRP with host ADB access;
* USB ADB from TWRP;
* Download Mode plus functioning Odin4/Heimdall path;
* another demonstrably reliable host-controlled recovery path.

Prefer having both TWRP and Download Mode recovery.

If the agent is physically unable to interact with buttons, determine whether:

```text
adb reboot recovery
adb reboot download
```

are sufficient from the current state.

Actually test recovery access **before** making the first Linux boot experiment.

If rebooting to TWRP causes wireless ADB to disappear, that is expected. Do not confuse lost Wi-Fi ADB with a failed recovery.

The host should have a USB connection available for destructive/recovery phases.

There is no requirement to use a microSD card.

If reliable recovery cannot be demonstrated, stop before destructive operations and report the missing physical requirement.

# Phase 9 — Internal UFS layout; no SD card

The final Linux root must live in a dedicated internal-UFS partition.

Use the SM-X910 dual-boot architecture as a conceptual model, but derive all numbers from X810.

Target layout conceptually:

```text
existing Samsung partitions
...
super        -> untouched Android dynamic partitions
userdata     -> recreated smaller for One UI
linuxroot    -> new ext4 Fedora root
...
```

Do not hardcode `userdata` as partition 34 or `linuxroot` as partition 35 until the X810 has been measured.

Because current Android userdata is disposable, do **not** attempt a risky live shrink of encrypted/F2FS userdata.

Instead:

1. back up the original GPT;
2. record PIT;
3. delete/recreate `userdata` at a smaller size;
4. create `linuxroot` in the freed space;
5. format/create the required filesystems from recovery;
6. allow Android to create fresh encryption state.

Make the split configurable.

A reasonable project interface would expose:

```text
ANDROID_PERCENT
```

instead of embedding a fixed sector count.

If no better use-case evidence emerges, choose a balanced default, but keep it easy to change before installation.

All actual partition boundaries must be sector-aligned and derived from the device's physical geometry.

Before applying a generated partition table, validate:

* first sector;
* last sector;
* partition order;
* backup GPT location;
* no overlap;
* alignment;
* preserved GUIDs/types where appropriate;
* exact untouched partitions;
* total disk geometry.

Save both:

```text
gpt-before.bin
gpt-after-planned.txt
```

on the host.

# Phase 11 — Root filesystem installation with no SD

The installation path should be host → recovery → internal `linuxroot`.

Preferred transport:

**ADB sideload or USB ADB from TWRP.**

Do not depend on files being present on Android userdata because that partition may be reformatted.

The Fedora installer should:

1. identify `linuxroot` by stable partition label/path;
2. verify size;
3. ensure it is unmounted;
4. create/check ext4;
5. install or write the Fedora root image;
6. read data back and verify it;
7. only after successful rootfs verification install the Fedora boot set.

The expensive/rootfs operation should happen before boot-chain replacement.

That preserves a valid Android boot set if the large write fails.

The desired stable state is an AVB-disabled vbmeta compatible with both One UI and Fedora.

Research the currently installed vbmeta and report:

* descriptors;
* verification state;
* whether it is on a read-only UFS LUN;

# Phase 32 — Handling interruption during boot-set switch

A four-partition swap is not truly atomic.

Study the Ultra implementation's failure strategy.

Improve reliability where practical:

* validate all four source images before writing the first;
* verify destination sizes before writing;
* save current set;
* write with fsync;
* read back each partition;
* never reboot on a failed hash;
* preserve TWRP independently.

Consider a deterministic write order.

Document what happens if power is lost after each individual partition write.

Recovery must always be possible by flashing a complete known-good set from TWRP.

Provide:

```text
tools/restore-boot-set.sh
```

that operates from recovery over ADB and accepts an explicit set directory.
